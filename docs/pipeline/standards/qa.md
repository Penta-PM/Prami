# QA 표준 프로파일 (⑦ 시스템 테스트 · ⑧ 지원)

공통 규칙·표기: `README.md`. 단계 정의: `docs/pipeline/v-model.md`.

> **QA 생략 모드 동안**: ⑦ 은 Dev 가 대신하고 "독립성 없음" 을 표시합니다. 테스트 설계 기법은 Plan(AC 도출)·Dev(테스트 작성)가 나눠 맡습니다. QA 세션은 요청이 올 때만 아래를 적용합니다.

## 넣기

### 1. 테스트 기초 — ISTQB CTFL v4.0.1
- **하는 일**:
  - 2장 테스트 레벨: ⑤ 단위 · ⑥ 통합 · ⑦ 시스템 · ⑧ 인수를 V모델 높이에 맞춰 구분합니다. QA 는 ⑦ 을 맡고 ⑤⑥ 결과는 Dev 기록(SHA·DB)으로 확인합니다.
  - 4장 테스트 기법: AC 마다 동등 분할·경계값·결정표·상태 전이 중 맞는 기법으로 케이스를 보탭니다. 경험 기반(탐색적) 테스트는 시간 상자를 정해 기록합니다.
  - 5장 관리: 진입 기준(Dev 게이트 기록 있음, SHA = PR head)·종료 기준(SR AC 전부 판정, CRITICAL 0)을 지킵니다. 결함 보고는 재현 절차·기대/실제·SHA·환경을 씁니다.
- **산출물**: `[검증 결과] PR #N` — SR AC 별 통과/실패 표, 결함 목록(심각도), `검증 SHA`.
- **생략**: 문서 수준(문서 검토·secret scan 만).

### 2. 모바일 — ISTQB CT-MAT v1.0
- **하는 일**: 모바일 작업은 화면 크기(320·360·390), 방향, 입력(터치·키보드 표시), 중단(전화·앱 전환 후 복귀), 네트워크 저하를 점검합니다. 에뮬레이션(Playwright Pixel 7)과 실기기(iOS Safari·Android Chrome) 결과를 구분해 적습니다.
- **산출물**: 결과 표에 `환경: 에뮬레이션 | 실기기(<기기>)` 열.
- **생략**: 모바일 화면 변경 없음.

### 3. 인수 테스트 — ISTQB CT-AcT v1.0 (Main 참고)
- **하는 일**: ⑧ 은 Main 이 맡습니다. 인수 기준(UR)과 AC(SR)를 함께 다듬는다는 원칙에 따라, QA 는 요청이 오면 인수 기준이 :3000 에서 관찰 가능한 문장인지 검토합니다.
- **산출물**: (요청 시) 인수 기준 검토 의견.
- **생략**: 생략 모드 동안 전부.
