# Dev 표준 프로파일 (④ 구현 · ⑤ 단위 · ⑥ 통합 · 생략 모드의 ⑦)

공통 규칙·표기: `README.md`. 단계 정의: `docs/pipeline/v-model.md`. 검증 절차: `docs/pipeline/verification.md`.

## 넣기

### 1. 구현·통합 — 12207:2026 §6.4.7 구현 · §6.4.8 통합 · §6.4.9 검증
- **하는 일**: 스펙의 SR·DS 범위 안에서 구현합니다. ⑤ 단위 → ⑥a 격리 DB integration → ⑦a 영향·SR 매핑 E2E 순으로 확인하고, 테스트 제목을 AC ID 로 시작합니다(`MOB-SR-101.2: …`).
- **산출물**: PR 본문 추적표(ID | 단계 | 테스트 | 결과), `## 로컬 검증`.
- **생략**: S 는 DS·⑥⑦ 행 생략(명령 자체는 게이트에서 실행).

### 2. 보안 개발 프레임워크 — NIST SP 800-218 SSDF v1.1
- **하는 일**: PW(잘 보호된 SW 생산) 중 PW.5 안전한 코딩, PW.7 코드 리뷰·분석, PW.8 테스트를 PR 마다 수행합니다. PS(저장소 보호)는 `check:secrets`·라벨 게이트로, RV(취약점 대응)는 CI 빨강·보안 결함 발견 시 즉시 수정 PR 로 대응합니다.
- **산출물**: PR `## 보안 체크`.
- **생략**: 문서 수준.

### 3. 시큐어코딩 — 행정안전부·KISA 「소프트웨어 개발보안 가이드」
- **하는 일**: 구현단계 보안약점 49개의 7분류(입력데이터 검증·표현, 보안기능, 시간·상태, 에러처리, 코드오류, 캡슐화, API 오용)로 변경분을 점검합니다. Prami 에서 자주 걸리는 것: 서버측 입력 검증, SQL 은 drizzle 파라미터만, 권한 확인 누락, 오류 메시지에 내부 정보 노출.
- **산출물**: 보안 체크 항목 옆에 `(KISA 입력데이터 검증)` 처럼 분류 표시.
- **생략**: 문서·순수 스타일 변경은 N/A 로 표시.

### 4. 검증 기준 — OWASP ASVS 5.0.0 (L1 기본, L2 해당 시)
- **하는 일**: 모든 PR 은 L1. 인증·세션·권한·원가·개인정보 경로를 바꾸는 PR 은 해당 장의 L2 까지. 주로 쓰는 장: V1 인코딩·살균, V2 검증·업무 로직, V3 웹 프런트엔드, V4 API, V6 인증, V7 세션, V8 권한, V13 설정, V14 데이터 보호, V16 로깅·오류. **4.x ID 와 섞지 않습니다.**
- **산출물**: 보안 체크 항목의 `(ASVS V8)` 표시, L2 적용 시 PR 에 "ASVS L2: V6·V8" 명시.
- **생략**: 문서 수준.

### 5. 코드 리뷰 — Google Engineering Practices (Code Review)
- **하는 일**: 머지 전 자기 diff 를 리뷰 관점(설계·기능·복잡도·테스트·이름·주석)으로 한 번 읽습니다. 기준은 "전체 코드 건강을 낫게 하면 승인". PR 은 작게 나눕니다(:3000 이 작업 브랜치를 서빙하므로도).
- **산출물**: PR 본문 요약에 리뷰 중 고친 것 1~3줄(없으면 생략).
- **생략**: 없음.

### 6. 시스템 테스트 대행 (QA 생략 모드) — ISTQB CTFL v4.0.1 4장 · CT-MAT v1.0
- **하는 일**: Plan 의 AC(Gherkin)를 E2E 로 옮깁니다. 경계값·상태 전이 AC 는 경계 양쪽을 다 씁니다. 모바일 작업은 CT-MAT 관점(화면 크기, 에뮬레이터 대 실기기, 입력 방식)으로 에뮬레이션 결과와 실기기 미확인을 구분해 적습니다.
- **산출물**: 추적표 ⑦ 행, `⑦ 수행: Dev (QA 생략 모드 — 독립성 없음)`.
- **생략**: S·문서 수준.
