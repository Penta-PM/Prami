### 2.2 원가 비중 계산 (Q3 A, Q4 A)
1. 위치: `server/cost/price-ratio.ts` `getCostRatios(access, priceRowIds)` — `CostAccess` 토큰 필수. **현재 페이지 행 id 만**.
   반환 `{ [priceRowId]: { ratio: number | null, reason?, costFrom?: date } }`. **원가 금액은 반환하지 않는다.** DB 에 저장하지 않는다.
2. 대상 행: 단가유형 **정상판매**(데이터 원문 값 그대로 비교) + 품목이 `cost_item_links` 에 있음. 그 외 행은 값 없음('—', 툴팁 없음).
3. 원가 선택: 매핑된 자재번호의 `material_costs` 중 표준구매원가·일반, 가격 행과 **같은 화폐**, `effective_from <= 가격.effective_from < effective_to(또는 NULL)`.
   같은 날짜 중복은 `effective_from` 최신 → `source_row` 최대로 tie-break. 이전 원가로 대체하지 않는다.
4. 비중 = 원가 / 판매가 × 100, 소수 1자리 반올림(half-up). 표시 `NN.N%`, 오른쪽 정렬.
5. '—' + 사유 툴팁(`title`·접근 가능한 설명): "해당 시기 원가 없음" / "판매가 0" / "화폐 불일치". 값이 있으면 툴팁 "원가 적용일 YYYY-MM-DD".
6. 감사: `/admin/costs` 페이지 조회와 같은 단위·방식으로 `cost.read` 기록(행마다 기록 금지).

### 2.3 노출·격리
1. 열 노출 = `pricing.write`(관리 화면) **그리고** `cost.read`. 둘 중 하나라도 없으면 열 정의 없음, RSC payload·응답에 키 없음(가림 `***` 아님).
2. 공용 가격 쿼리(`getPriceRows`)·`/pricing`·챗봇(`priceSelection`, chat 도구)은 **원가 관련 변경 0**. 비중은 별도 prop(`costRatios`)으로 관리 화면에만 전달.
3. 필드 이름에 `cost` 포함(`costRatio`) — 챗봇 가드 `assertNoCostKeys` 가 혹시 섞여도 차단.
4. 1차는 **정렬 불가**(`sortable:false`, 서버 화이트리스트 미등록 — `sort=costRatio` 는 무시돼 기본 정렬). 행 상세 드로어에는 넣지 않는다.
5. 열 위치: 관리 표 기본 순서에서 '판매가' 바로 뒤. 최소 폭 약 72px, 헤더 줄바꿈 금지. #32 저장 레이아웃 정규화로 기존 사용자에게 자동 삽입.

### 2.4 가격 변동 열 (Q5 A)
1. 새 열 **'가격 변동'**. 기존 '비고'(ERP 원문)는 무변경. **전체 행**, 조회(`/pricing`)·관리 화면 모두 표시(원가 정보 아님).
2. 이전 = 같은 계열(품목코드+단가유형+단가구분+화폐+고객)의 **직전 적용시작일 행**(삭제 행 제외). 필터·페이지와 무관하게 전체 데이터 기준
   (윈도 `lag(unit_price) over (partition by 계열 order by effective_from)` 를 필터 적용 **전** 집합에서 계산).
3. 변동률 = (현재 − 이전) / 이전 × 100, 소수 1자리 반올림. 표시: `▲ 이전 대비 N.N% 상승` / `▼ 이전 대비 N.N% 하락` / `변동 없음` / 첫 시기·이전가 0 은 `—`.
   화살표는 `aria-hidden`, 상승·하락은 텍스트로 구분, 색은 기존 토큰(라이트·다크 대비 확인).
4. 정렬 가능: 정렬 id `priceChange`(숫자, NULLS LAST)를 서버 화이트리스트와 클라이언트 비교에 함께 등록(#32 §9.3 규칙).

## 8. 가격 변동 윈도 성능 (2026-10-21, Dev msg_fa3ccec647bc — 큐 7)
- **결정: C — 지금은 A(2단계 좁히기, 마이그레이션 없음), B(파생 컬럼)는 필요 시 별도 스펙.**
