- 근거 사례: #109 제품 칩 색 — 머지 전 미리보기로 사용자가 방향을 바로 수정(계산기 원복 + 표 칩).
- 해석(Main 과 같음): ":3000 확인이 CI·머지를 기다리지 않게". **CI 는 main 머지 게이트로 그대로 유지**. QA 생략 모드 유지. 보안 규칙 그대로.
- 병렬 검토 생략: 제품 기능이 아니라 역할 절차 변경(설계는 Main 이 Plan 에 위임). 제품 코드는 §6 표시 배너 1건뿐(경량).

## 1. 새 흐름
```
Plan 배정 → Dev 구현(작업 워크트리 wt-*) → [미리보기 게이트] → :3000 = 작업 브랜치 커밋
   → Dev → Main "[미리보기 준비됨]" (+ Plan 한 줄)  → 사용자 확인
   → 피드백(Main → Plan → Dev, 방향이 바뀌면 Plan 이 스펙 갱신) → 같은 브랜치 수정 → :3000 갱신 → 반복
   → 사용자 OK(또는 피드백 없음) → Dev 게이트 + CI 녹색 → 셀프머지 → :3000 = main 복귀 → 완료 보고
```
- 미리보기는 **머지 조건이 아님**. 사용자 OK 를 기다리지 않고 게이트·CI 를 병행해도 되며, 피드백이 오기 전 머지됐다면 수정은 후속 PR.
- 단, Main 이 "확인 후 머지" 라고 지정한 작업은 사용자 OK 전 머지 금지.

## 2. 미리보기 게이트 (최소, 빠르게)
- 작업 브랜치에 **커밋·푸시된 SHA** 만 띄움(미커밋 변경 금지 — 재현 가능해야 함). Dev 워크트리에서 직접 개발하지 않음.
- 그 SHA 에서 typecheck 통과 + 바뀐 영역 단위 테스트 통과.
- 전환 후 :3000 `/login` 200 + 볼 곳 각 페이지 200(로그인 세션 기준), dev 서버 로그에 컴파일 오류 없음.
- 의존성(lockfile) 변화가 있으면 `pnpm install --frozen-lockfile --offline`(실패 시 미리보기 보류, Plan 에 보고). main 복귀 때도 동일.
- 실패하면 즉시 main(또는 직전 미리보기 SHA)으로 되돌리고 보고.

## 3. :3000 슬롯 — 한 번에 한 브랜치
- 기본: **사용자가 지금 확인 중인(가장 최근 "[미리보기 준비됨]" 을 받은) 작업** 이 슬롯을 가짐.
- 다른 작업이 미리보기 준비되면 Dev 는 바로 바꾸지 않고 Main 에 "[미리보기 대기] <작업> — 현재 슬롯: <작업>" 을 알림. Main(사용자)이 바꿀지 정함. 사용자가 이미 OK 했거나 머지된 작업이면 바로 교체 가능.
- 피드백 대기 중인 작업이 30분 넘게 반응이 없고 다른 작업이 대기 중이면 Dev 가 Main 에 교체를 물어봄(임의 교체 금지).
- 두 작업을 합친 통합 브랜치 미리보기는 하지 않음(충돌·혼선).
- 긴급 버그 수정은 Main 지시로 슬롯 선점 가능.

## 4. 마이그레이션이 있는 작업
- LAN DB 는 수집기가 쓰는 공용 DB 라 미리보기도 규칙 동일: **추가형만, 적용 전 pg_dump 백업 + 경로 보고**.
- 추가로: 마이그레이션 SQL 이 **확정(스키마 동결)** 된 뒤에만 LAN 에 적용. 스키마가 아직 바뀔 수 있으면 미리보기는 Dev 자기 포트(:32xx) + 합성 DB 로 하고 :3000 은 UI 가 스키마와 무관한 경우만.
- 미리보기 중 적용한 마이그레이션은 main 머지 때 **같은 파일·같은 번호**여야 함(drizzle journal 일치). 피드백으로 스키마를 바꿔야 하면 새 추가형 마이그레이션을 더하거나, Plan 승인 하에 검토된 down SQL 로 추가분만 제거 후 재적용(백업 복원은 수집기 데이터 손실이 있어 최후 수단, Main 승인).
- 작업이 취소되면 Plan 이 정리 방법(추가 객체 제거 / 유지)을 결정.
- `procurement-import --replace` 금지 등 수집기 관련 규칙 그대로.

## 6. 미리보기 표시 (제품 코드, 경량 PR-PV)
- :3000 이 main 이 아닐 때 화면 맨 위에 얇은 띠: "미리보기 중 — <브랜치> @ <SHA 7자> (main 아님)". warning-50 배경 + warning-800 글자, 14px, 높이 28px, 닫기 없음, `role="status"`.
- 조건: `NODE_ENV === 'development'` 이고 현재 git 브랜치 ≠ main(또는 detached HEAD). **요청 시점에 읽음**(HMR 로 브랜치가 바뀌어도 서버 재시작 없이 반영) — 서버 컴포넌트에서 워크트리 `.git` → gitdir 의 HEAD 를 fs 로 읽고 짧게(≈5초) 캐시. 실패하면 띠 없음(조용히).
- 프로덕션 빌드에서는 코드 경로 자체가 실행되지 않음(번들에 git 경로·SHA 외 정보 노출 없음). 비밀값·경로 전체는 화면에 표시하지 않음(브랜치명·SHA 7자만).
- 수용 기준: 단위(브랜치 main → 없음, feat/x → 띠, detached → 띠, 읽기 실패 → 없음, production → 없음) + Dev 게이트 + CI 녹색 → 셀프머지.
